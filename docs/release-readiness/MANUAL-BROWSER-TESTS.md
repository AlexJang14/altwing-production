## Two local previews, with different purposes

**Standalone assessment/report preview:** download and open the current `preview.html`. It runs the actual assessment/report components with clearly labelled synthetic fixtures. It can exercise five questions, close/reopen, story, permissions, report filters, CSV and print/PDF. It cannot prove integration with the real WingMatch result or database storage. Its access-state buttons simulate expected roles; they are not authentication.

**Complete frontend preview on your own computer:** use the reviewed editable `source/` from the package. Use Node **22.13+** or the tested Node24. In a terminal inside that source folder:

```sh
npm run install:ci
npm run build:pages:preview
ALTWING_PAGES_TARGET=preview npm exec -- vite preview --config vite.pages.config.ts --host 127.0.0.1 --port 4173 --strictPort
```

On Windows PowerShell, set `$env:ALTWING_PAGES_TARGET="preview"` on its own line before the same `npm exec -- vite preview ...` command. Open **http://127.0.0.1:4173/altwing-production/**. Stop the server with Ctrl+C when finished. This is a local instruction for the reviewer; no preview server/browser was started by the assistant. Do not push, publish, use production build flags, add secrets, or change DNS.

The preview build disables automatic production telemetry and real feedback submissions. Its API hostname remains the existing backend configuration, but production gates reject sending from previews. A local feedback submission must show the development/preview-disabled error, not a fake success. Use the standalone **demo** preview to test the successful receipt layout without a database write. Do not change Origin headers or spoof authentication to make a local request reach production.

Use a dedicated browser profile/private window for QA. Do not clear data on `altwing.org`; that could remove real saved progress. Clear only **127.0.0.1:4173** between tests that require a fresh visitor. Retain the private profile during persistence tests. Desktop minimum: current Chrome or Edge and Firefox; also Safari if available. Mobile: one actual iPhone/Safari and one actual Android/Chrome where available; mark missing coverage UNVERIFIED. Responsive emulation is additional evidence, not a replacement for a physical keyboard/touch/soft-keyboard test.

The impact-v3 wording/submission revision updates D04–D07, A03 and P01. Prior candidate results must be rerun for these changed interactions; no manual test is automatically marked passed. The same 38 case IDs are retained.
